# 路由配置与断言工厂实战

## 课程目标

- 理解断言（Predicate）在Gateway路由匹配中的核心地位，以及它与过滤器的分工
- 掌握断言工厂的两种配置写法：短写法（Shortcut）与长写法（Full Configuration）
- 掌握最常用的断言工厂：`Path`、`Method`、`Header`、`Query`、`Host` 的配置语法与匹配规则
- 理解多个断言之间的“与”关系、短路求值机制及其对路由设计的影响
- 完成图书管理系统网关路由的多维度匹配改造：从“只看路径”扩展到“路径+方法+Header+参数”的组合控制



## 回顾与导入

上一节我们完成了Gateway的快速上手：创建了`book-gateway`模块，配置了三条显式路由，分别将`/api/products/**`、`/api/users/**`、`/api/orders/**`转发到对应的后端服务。当时的断言只有`Path`一种：

```yaml
predicates:
  - Path=/api/products/**
```

`Path`断言解决了“**按路径分流**”的问题，但真实的路由需求往往更精细：

> **场景一：** `/api/orders/**`下既有查询接口（GET），也有创建接口（POST）。如果只想对写操作做特殊处理（如限流），需要路由能区分HTTP方法。
>
> **场景二：** book-order的某些接口只对携带特定Header的客户端开放（如`X-Client-Version: 2.0`），需要在网关层做第一道筛选。
>
> **场景三：** 搜索接口`/api/products/search`，只有携带`keyword`参数时才走特定的下游服务，不带参数时走默认逻辑。
>
> **场景四：** 灰度发布时，只有携带`X-Gray-Tag: v2`的请求才转发到v2版本的后端实例——这正是标签化负载均衡在**网关入口**的提前分流。

这些需求，`Path`断言单独无法满足。Spring Cloud Gateway内置了十余种断言工厂，覆盖路径、方法、Header、Query参数、Host、Cookie、时间窗口、源IP等多个维度。本节从断言工厂的**配置模型**讲起，再逐一实战六种最常用的断言，最后完成一个“多维度组合路由”的完整配置。



## 断言工厂的核心模型

### 断言是什么

断言（Predicate）本质上是一个**返回布尔值的判断函数**，输入是当前的HTTP请求，输出是“是否匹配当前路由”。当一个请求到达网关时，Gateway会遍历所有路由，对每条路由的断言集合逐一求值。只有**当前路由的所有断言都返回`true`**，请求才会被转发到该路由的`uri`。

| 角色       | 职责                                              |
| ---------- | ------------------------------------------------- |
| **断言**   | 判断“这个请求是否应该走这条路由”                  |
| **过滤器** | 在请求转发前后，对请求/响应做加工（后续内容展开） |

> **断言决定“去不去”，过滤器决定“怎么去”。** 本节只关注断言。

### 两种配置写法：短写法 vs 长写法

Spring Cloud Gateway的断言有两种写法，功能完全等价，只是表达方式不同。

**短写法（Shortcut Configuration）** 是最常用的形式，格式为`断言名称=参数1, 参数2, ...`：

```yaml
predicates:
  - Path=/api/products/**
  - Method=GET,POST
  - Header=X-Client-Version, 2\.0
```

**长写法（Full Configuration）** 更显式，适合需要配置额外参数的场景：

```yaml
predicates:
  - name: Path
    args:
      patterns: /api/products/**
      matchTrailingSlash: true
  - name: Method
    args:
      methods: GET,POST
```

| 维度         | 短写法           | 长写法                                     |
| ------------ | ---------------- | ------------------------------------------ |
| 简洁度       | 高               | 低                                         |
| 可读性       | 适合简单断言     | 适合复杂参数                               |
| 额外参数支持 | 通过逗号位置传递 | 通过`args`键值对，更明确                   |
| 推荐场景     | 日常配置         | 需要设置`matchTrailingSlash`等非默认参数时 |

> **本节统一使用短写法**，在需要额外参数时再引入长写法。

### 断言之间的逻辑关系：AND + 短路

一条路由配置多个断言时，它们之间是**逻辑“与”（AND）** 的关系：所有断言都为`true`，路由才匹配。

```yaml
predicates:
  - Path=/api/orders/**
  - Method=POST
  - Header=X-Client-Version, 2.0
```

以上路由要求：路径匹配`/api/orders/**` **且**方法是`POST` **且**Header `X-Client-Version`的值匹配`2.0`。三者缺一不可。

执行机制是**按声明顺序依次判断，短路求值**：一旦某个断言返回`false`，后续断言不再执行，直接判定该路由不匹配。这意味着：

| 影响                             | 说明                                                         |
| -------------------------------- | ------------------------------------------------------------ |
| 断言顺序影响性能                 | 把**最容易失败**的断言放在前面（如`Method`），可以尽早短路，减少不必要的判断 |
| 断言顺序不影响结果               | 在“全为AND”的语义下，顺序不改变最终匹配结果，只影响执行开销  |
| 单个断言异常导致整条路由匹配失败 | 如果某个断言的正则语法错误，会抛出异常，该路由无法匹配       |

> **不要试图用多个断言实现“或”的逻辑。** 如果需要“路径A **或** 路径B”，应该在一条路由的`Path`断言中写多个模式，或声明两条独立的路由，而不是依赖断言之间的组合。



## 六种常用断言工厂实战

### Path：路径匹配

`Path`是使用频率最高的断言，基于Ant风格路径表达式进行匹配。

| 通配符 | 含义                     | 示例                                                         |
| ------ | ------------------------ | ------------------------------------------------------------ |
| `*`    | 匹配**单个**路径段       | `/api/*/products` 匹配 `/api/v1/products`，不匹配 `/api/v1/v2/products` |
| `**`   | 匹配**任意数量**的路径段 | `/api/**` 匹配 `/api/products`、`/api/products/1` 等         |

**多模式配置：** 一个`Path`断言可以接受多个模式，用逗号分隔：

```yaml
- Path=/api/products/**,/api/stock/**
```

**路径变量：** `Path`支持命名路径段，供过滤器使用：

```yaml
- Path=/api/v{version}/products/**
```

> **`matchTrailingSlash`参数：** 默认情况下，`Path=/api/products`**不会**匹配`/api/products/`（带尾部斜杠）。如果需要匹配，使用长写法设置`matchTrailingSlash: true`。

### Method：请求方法匹配

`Method`断言按HTTP方法匹配，可以指定一个或多个方法：

```yaml
- Method=GET
- Method=GET,POST,PUT,DELETE
```

**典型用途：** 将同一路径下的读操作和写操作路由到不同的后端服务或应用不同的过滤器策略。

### Header：请求头匹配

`Header`断言检查请求中是否包含指定名称的Header，且**值匹配给定的正则表达式**。

**短写法（单参数，只检查Header存在）：**

```yaml
- Header=X-Request-Id
```

**短写法（双参数，名称+正则）：**

```yaml
- Header=X-Request-Id, \d+
- Header=Authorization, Bearer.*
- Header=X-Client-Version, 2\.0
```

| 配置                             | 匹配条件                         |
| -------------------------------- | -------------------------------- |
| `Header=X-Request-Id`            | 请求包含`X-Request-Id`头，值不限 |
| `Header=X-Request-Id, \d+`       | 请求包含该头，且值**全为数字**   |
| `Header=Authorization, Bearer.*` | 值以`Bearer`开头                 |

> **Header值的正则匹配是“完全匹配”还是“部分匹配”？** 默认是**完全匹配**（`matcher.matches()`），即正则必须覆盖整个Header值。`Bearer.*`能匹配`Bearer token`，但`\d+`只能匹配纯数字的完整值，不能匹配`abc123`。

### Query：查询参数匹配

`Query`断言检查请求URL中是否包含指定的查询参数，并可选择性地匹配参数值的正则表达式。

**仅检查参数存在（不关心值）：**

```yaml
- Query=keyword
```

**检查参数存在且值匹配正则：**

```yaml
- Query=keyword, .*
- Query=type, admin|editor
```

**典型组合——路径+参数：**

```yaml
- id: search-route
  uri: lb://book-product
  predicates:
    - Path=/api/products/search
    - Query=keyword
```

> **`Query`断言只匹配URL中的查询参数**（`?key=value`），不匹配表单体或JSON体中的字段。

### Host：主机名匹配

`Host`断言按请求的`Host`头匹配，支持通配符：

```yaml
- Host=api.example.com
- Host=**.example.com
```

| 配置                   | 匹配的Host                                         |
| ---------------------- | -------------------------------------------------- |
| `Host=api.example.com` | 仅精确匹配                                         |
| `Host=**.example.com`  | `api.example.com`、`blog.example.com` 等所有子域名 |

> **本机开发时**，`Host`通常是`localhost:8080`，`Host`断言的实用价值有限，主要在多域名部署场景中使用。

### Cookie：Cookie匹配

`Cookie`断言检查请求中是否包含指定名称的Cookie，且值匹配正则：

```yaml
- Cookie=sessionId, [a-f0-9]+
- Cookie=user
```

| 配置                          | 匹配条件                           |
| ----------------------------- | ---------------------------------- |
| `Cookie=user`                 | 包含名为`user`的Cookie，值不限     |
| `Cookie=sessionId, [a-f0-9]+` | 包含该Cookie，且值全为十六进制字符 |

> **`Cookie`断言一次只能匹配一个Cookie键值对。** 需要校验多个Cookie时，配置多个`Cookie`断言（它们之间是AND关系）。

### 断言工厂速查表

| 断言     | 短写法示例                      | 核心用途         |
| -------- | ------------------------------- | ---------------- |
| `Path`   | `Path=/api/products/**`         | 按路径分流       |
| `Method` | `Method=GET,POST`               | 按HTTP方法分流   |
| `Header` | `Header=X-Client-Version, 2\.0` | 按客户端特征分流 |
| `Query`  | `Query=keyword`                 | 按查询参数分流   |
| `Host`   | `Host=**.example.com`           | 按域名分流       |
| `Cookie` | `Cookie=sessionId, [a-f0-9]+`   | 按Cookie分流     |



## 实战一：为book-order路由增加方法断言

### 目标

让book-order的写操作（`POST`）和读操作（`GET`）走两条不同的路由，为后续“只对写操作做特殊处理”留出空间。

### 配置

```yaml
- id: book-order-read-route
  uri: lb://book-order
  predicates:
    - Path=/api/orders/**
    - Method=GET
- id: book-order-write-route
  uri: lb://book-order
  predicates:
    - Path=/api/orders/**
    - Method=POST,PUT,DELETE
```

### 验证

| 请求                                        | 匹配的路由               |
| ------------------------------------------- | ------------------------ |
| `GET http://localhost:8090/api/orders/1`    | `book-order-read-route`  |
| `POST http://localhost:8090/api/orders`     | `book-order-write-route` |
| `DELETE http://localhost:8090/api/orders/1` | `book-order-write-route` |

**观察方式：** 在网关日志中输出路由ID，确认请求命中了预期的路由。

```yaml
logging:
  level:
    # 针对路由匹配的核心类，输出 TRACE 级别日志（会显示匹配过程）
    org.springframework.cloud.gateway.handler.RoutePredicateHandlerMapping: TRACE
```



## 实战二：为book-product搜索路由增加Query断言

### 目标

例如：book-product的`/api/products/search`接口需要`keyword`参数才有意义。在网关层增加`Query=keyword`断言，让“缺少keyword的搜索请求”不匹配这条路由（从而返回404，而不是透传到后端再报参数错误）。

### 配置

```yaml
- id: book-product-search-route
  uri: lb://book-product
  predicates:
    - Path=/api/products/search
    - Query=keyword
```

### 验证

| 请求                                      | 结果                                                        |
| ----------------------------------------- | ----------------------------------------------------------- |
| GET /api/products/search?keyword=Spring   | 匹配，转发到book-product                                    |
| GET /api/products/search（无keyword）`    | **不匹配**，返回404                                         |
| GET /api/products/search?keyword=（空值） | **匹配**（`Query=keyword`只检查参数存在，不检查值是否非空） |



## 实战三：组合断言实现多维度路由

### 目标

为book-product的“写操作”增加Header校验：只有携带`X-Admin-Token`的请求，才允许通过网关调用`POST /api/products`（创建商品）。这是“网关层第一道鉴权”的简化演练。

### 配置

```yaml
- id: book-product-admin-write-route
  uri: lb://book-product
  predicates:
    - Path=/api/products
    - Method=POST
    - Header=X-Admin-Token, .+
```

### 验证

| 请求                                      | 结果                              |
| ----------------------------------------- | --------------------------------- |
| POST /api/products 无X-Admin-Token        | **不匹配**，返回404               |
| POST /api/products 携带X-Admin-Token: any | **匹配**，转发到book-product      |
| GET /api/products 携带X-Admin-Token       | **不匹配**（`Method`断言拒绝GET） |

> **三条断言的关系：** `Path` 且 `Method` 且 `Header`，三者全部满足才匹配。`Header`的正则`.+`表示“至少一个字符”，即Header值不能为空。




## 小结

本节课我们学习了：

1. **断言的核心定位**：判断“请求是否匹配路由”，所有断言为`true`才转发；与过滤器（“怎么去”）分工明确。

2. **两种配置写法**：短写法（`断言=参数`）简洁高效，长写法（`name` + `args`）支持额外参数如`matchTrailingSlash`。

3. **断言之间的AND + 短路机制**：所有断言为`true`才匹配；按声明顺序执行，任一返回`false`即短路；顺序影响性能但不影响结果。

4. **六种常用断言工厂**：`Path`（Ant风格路径）、`Method`（HTTP方法）、`Header`（Header存在+正则）、`Query`（参数存在+正则）、`Host`（域名通配符）、`Cookie`（Cookie键值+正则）。

5. **多维度组合路由**：`Path` + `Method` + `Header` 的组合，实现了“路径正确 + 方法正确 + 客户端特征正确”的精确路由控制。

6. **路由声明顺序的重要性**：更具体的路由必须放在更宽泛的路由之前，否则会被宽泛路由抢先匹配。
